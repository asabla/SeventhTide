# Seventh Tide UX

Seventh Tide is a game for friends playing from separate screens and for one player with bots. Each player sees their own hand, the crew’s public condition, and the cards played this tide. Review from the seat affected by the change. Use a guest seat as well as the host when a change affects what friends see or do.

## Design from the raft

Start from the latest design the user approved. Open the matching state in the running game and look at the whole screen. Older review screenshots can show how a feature evolved. Use the current approved design to make decisions about placement, materials, type, scale, and spacing.

| Surface               | Design                                                                                                                                                    |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Hand and played cards | Use the illustrated, parchment card face. Show the effect and cost on the choice. Carry the same illustration into the public play.                       |
| Play tray             | Keep the wet metal tray focused on committing the local sailor’s choice. Put public plays on the table outside the tray.                                  |
| Ship’s log            | Use ruled paper, ledger typography, and ink annotations. Keep condition and crew callouts here. Retain the same materials and hierarchy at narrow widths. |
| Header tools          | Use the illustrated objects beside the wordmark for secondary interactions such as entries, rules, and signals.                                           |

Use the tool rail for actions that keep both equipment cards. Carry the same tool marker into the public play. Show route options on a single shared chart with controls for the host and previews for guests. Give the line handoff priority when boarding. Put the previous tide’s recap within reach below it.

Reuse the closest approved surface before making a new one. Inspect illustrations at the actual rendered size against the nearby card art. A new asset must read clearly in its crop and depict the action it represents.

## Verify in the running game

1. Capture the starting state when correcting an existing interaction. Save enough of the board to show the surrounding layout.
2. Run the normal player flow at a desktop width and a phone-width browser viewport. Check the placement, material, typography, art crop, and text at normal zoom. Scroll wherever the player needs to scroll.
3. Perform the changed interaction through its result. Where applicable, check idle, selected, opened, committed, and unavailable states. Check dismissal, focus, and keyboard operation for disclosures and dialogs. Verify that nearby interactions such as an already selected card still work.
4. Compare the final views with the approved reference and correct mismatches. Capture the final decision and its result in screenshots or a short recording.
5. Put the visual evidence in a PR comment. Caption each view with the seat, state, and interaction it demonstrates. State any state or viewport that could not be checked.

Record browser viewport checks as such. Test results and simulation runs verify logic. The review images and exercised browser flow verify the player experience.
